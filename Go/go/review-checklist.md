# Go Code Review 检查清单

审查目标是判断改动是否正确、安全、可维护，以及验证是否足以支持合并。按改动风险选择审查深度，不要求每个改动都用相同方式逐行检查。

## 先理解改动

- 改动要解决什么问题？实现是否符合需求和已有设计？
- 实际 diff 是否超出所需范围，是否包含无关重构或生成文件变化？
- 新增的行为、兼容性变化和限制是否有说明？

## 正确性与故障路径

- 正常路径、错误路径、边界值和空值是否都处理正确？
- 错误是否被检查、包装并在正确的边界处理？是否意外丢失根因或重复记录？
- 资源是否在成功和失败路径上释放？循环、超时或提前返回时是否会泄漏？
- 外部输入是否校验？重试、重复请求或部分失败会不会造成数据损坏或重复副作用？
- 并发访问是否有明确同步和所有权？goroutine、channel、锁和取消路径是否能正常收敛？

## 影响面与安全性

- 是否改变公共 API、配置、持久化格式、数据库结构或用户可见行为？不兼容变化是否说明影响和迁移方式？
- 权限、认证、输入校验、敏感数据和日志内容是否安全？新增或升级的依赖是否经过必要性与已知漏洞检查？
- 是否影响性能、内存、连接数、队列长度或外部服务负载？
- 是否触及高影响区域，例如认证授权、数据迁移、并发控制、依赖升级、CI、构建、发布或安装流程？

## 验证证据

- 是否有针对新行为或缺陷修复的测试？关键边界和失败路径是否覆盖？
- 作者实际运行了哪些格式化、静态检查、测试和构建？结果是什么？
- 未执行的检查是否说明原因及尚未覆盖的风险？
- 对 UI、协议或生成产物等非纯代码行为，是否提供了适合该改动的可观察验证证据？

## 审查意见的写法

- 阻塞性问题应指向具体文件和代码位置，并说明触发条件、影响和建议方向。
- 将本次改动引入的问题与原有问题区分开；原有问题不能归责于本次改动，但可单独记录。
- 区分必须修复的问题与可选的风格建议；避免提交没有实际影响的 nit。
- 不确定时说明假设或请求证据，不根据文件名或代码表面推断未证实的缺陷。
- 每条意见都应有处理结果：修复、补充验证，或由作者说明理由后关闭。

## 风险分级建议

以下分级用于决定审查力度，具体项目可按影响面调整：

| 风险 | 常见例子 | 建议审查 |
| --- | --- | --- |
| 低 | 文档、注释、无行为变化的整理 | 自动检查通过后，由作者确认改动和结果 |
| 中 | 一般业务逻辑、内部 API 或普通依赖变更 | 至少一位熟悉相关代码的人审查 |
| 高 | 权限、数据迁移、并发核心路径、发布/CI/安装流程、不可逆操作 | 相关负责人审查；要求针对风险的验证和明确回滚方案 |

风险由改动本身和潜在影响决定，不由作者身份决定。自动化评审可以提供发现，不能代替高风险改动所需的人工判断与责任。

## 审查收敛

- 第一轮后，后续审查重点看新增 diff 和未解决问题，同时确认此前问题已正确修复。
- 同一轮发现某类问题时，检查类似位置是否也有同类缺陷。
- 若多轮仍不断出现新问题，应重新评估整体方案，而不是无限追加局部修补。
- 不重复提出已处理或已说明的意见；确有新证据时再重新打开讨论。
