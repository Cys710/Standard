# Go 编码标准

本标准适用于一般 Go 服务、命令行程序和库。项目可根据自身约束补充细则。

## 格式与命名

- 使用 `gofmt` 格式化 Go 源码；提交的代码不应依赖编辑器的个人格式设置。
- 包名使用简短、小写、清晰的名称，避免无意义缩写和与常用标识符冲突的名称。
- 导出标识符使用符合 Go 惯例的 MixedCaps 命名；缩写的大小写保持一致，例如 `URL`、`ID`。
- 避免冗余命名。包名已经表达上下文时，包内名称通常不必重复包名。
- 注释应说明导出 API 的用途、约束或容易误用之处，不重复代码本身显而易见的内容。

## 工具链与依赖

- 在 `go.mod` 中声明项目支持的 Go 版本；CI 至少运行格式检查、`go vet`、测试和构建。
- 引入或升级依赖时，说明必要性，并检查其维护状态、许可证和已知漏洞；密钥等敏感配置不得硬编码或写入日志。

## 包与接口

- 按职责组织包；避免一个包同时承载无关领域，也避免为了目录层级而拆出只有转发代码的包。
- 接口优先由使用方定义，保持小而聚焦；不要仅为 mock 或“以后可能扩展”预先抽象。
- 导出类型、函数和方法构成公共 API。新增或修改时，考虑调用方是否依赖其行为、零值和错误语义。
- 公共 API、配置、持久化格式或协议有不兼容变化时，应说明影响、迁移方式；适用时提供弃用过渡。
- 避免不必要的全局可变状态。共享状态应有明确的所有权和并发保护方式。

## 错误处理

- 检查可能失败的操作返回的错误，不要无故丢弃错误；若确实可以忽略，应让理由清楚可见。
- 在错误边界补充有用的上下文。需要保留错误链时使用 `%w`，并在调用方需要判断时使用 `errors.Is` 或 `errors.As`。
- 不要仅为了日志记录而在多个层级重复记录同一个错误；在能够作出处理或提供有价值上下文的边界记录。
- 普通运行失败通过错误返回，不用 `panic` 代替正常控制流。只有程序无法安全继续的不可恢复状态才考虑 panic。
- 错误信息应便于定位问题，不应包含密码、令牌、密钥或不必要的个人数据。

## 并发与 Context

- 启动 goroutine 时说明它何时结束、由谁等待，以及取消或失败如何传播；避免无界 goroutine、任务或队列增长。
- 对共享可变数据使用互斥锁、原子操作、channel 所有权约定或其他明确同步机制；不能依赖“通常不会同时发生”。
- 不要在持有锁时执行可能阻塞或调用外部代码的操作，除非锁的范围和影响已经审慎评估。
- 将 `context.Context` 作为需要取消、超时或传递请求级元数据的操作的首个参数；不要传入 nil，也通常不要把请求 context 存入长期存在的结构体。
- 超时应由调用方根据操作边界设置；收到取消信号的代码应及时停止工作并释放资源。
- 服务关闭时应停止接收新工作，等待在途任务结束，并释放持有的资源。

## 资源与外部输入

- 成功取得资源后，尽早安排关闭或释放；确认错误后再 `defer` 清理，避免对无效资源调用清理方法。
- 注意循环中的 `defer` 会延迟到函数返回才执行；循环处理大量资源时，应使用明确的局部清理边界。
- HTTP 客户端调用应处理错误并关闭响应体；服务端应设置与业务相符的超时和请求大小边界。
- 校验来自网络、文件、环境变量和用户输入的数据；不要仅依赖上游保证输入正确。
- 对文件、网络和数据库操作考虑部分失败、重试、超时及重复执行的后果。

## 测试与可维护性

- 测试应验证可观察的行为、错误语义和重要边界，不要只验证实现细节。
- 测试应可重复运行，不依赖未声明的执行顺序、外部个人环境或真实生产数据。
- 修复缺陷时，尽可能添加能复现原问题的回归测试。
- 优先采用简单直接的实现。新增抽象、依赖或配置项时，说明它解决的当前问题及维护成本。
- 日志应包含排查所需的上下文，但避免敏感信息；库代码通常不应擅自决定应用的日志策略。
